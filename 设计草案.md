# DND 模组生成工作流设计草案

## 1. 项目目标

构建一个**人类把关的 DND 模组逐步生成系统**。

系统不追求让 Agent 完全自主完成全部创作，而是采用：

```text
确定性工作流 + RAG 检索 + LLM 生成节点 + LLM 审计节点 + 人类确认节点 + Artifact 版本管理
```

核心目标：

1. 基于少量核心资料生成 DND 模组。
2. 模组生成逐层展开，而不是一次性生成完整长文。
3. 每一步都允许人类确认、提出修改意见、回滚到上一状态。
4. 故事生成和世界观审计分离。
5. 所有中间产物可追踪、可版本化、可复用。
6. 控制 API 成本，把贵模型主要用于故事质量关键环节。

---

## 2. 核心资料范围

第一版只处理 4 类核心文档：

```text
1. 世界观文档
2. 玩家手册 / SRD
3. 城主指南 / SRD
4. 怪物手册 / SRD
```

这类规模不需要 RAGFlow、Dify 等重型知识库平台。第一版采用轻量 RAG 层即可。

建议公开产品场景优先使用 SRD 或确认授权范围。D&D Beyond 的 SRD 页面说明，SRD 包含可用于并引用以在 Creative Commons 下发布内容的 D&D 规则内容。([D&D Beyond][1])

```text
┌────────────────────┐
│      Frontend      │
│  Next.js + React   │
└─────────┬──────────┘
          │
          ▼
┌────────────────────┐
│      Backend       │
│      FastAPI       │
└─────────┬──────────┘
          │
          ▼
┌────────────────────┐
│ Workflow Engine    │
│ LangGraph          │
└──────┬─────┬───────┘
       │     │
       │     └────────────────────────┐
       │                              │
       ▼                              ▼
┌────────────────────┐       ┌────────────────────┐
│ Artifact Database  │       │ RAG Knowledge Layer│
│ PostgreSQL / SQLite│       │ Chroma / LanceDB   │
└────────────────────┘       └────────────────────┘
       │                              │
       ▼                              ▼
┌────────────────────┐       ┌────────────────────┐
│ Story Generator    │       │ World Auditor      │
│ GPT                │       │ DeepSeek           │
└────────────────────┘       └────────────────────┘
```

第一版可以用：

```text
Frontend: Next.js + React + Tailwind
Backend: FastAPI
Workflow: LangGraph
RAG: Docling + LlamaIndex + Chroma
Database: SQLite 或 PostgreSQL
LLM:
  - 故事生成：GPT
  - 世界观审计：DeepSeek
  - 资料整理：不做 LLM Agent，先由 RAG ingestion pipeline 替代
```

LangGraph 适合这个项目，因为它提供有状态图、checkpoint、人类介入和暂停恢复能力。官方文档说明，checkpointer 可以支持 human-in-the-loop，使人类能检查、打断、批准 graph 步骤，并在人工更新状态后恢复执行。([LangChain 文档][2])

## 4. 核心设计判断

### 4.1 第一版不需要“资料整理 Agent”

之前设想的资料整理 Agent，在当前规模下可以退化为：

```text
Knowledge Builder
= 文档解析 + heading-aware chunk + metadata 标注 + embedding + 检索接口
```

也就是说：

```text
资料整理 Agent
≈
RAG Ingestion Pipeline
```

第一版先不做：

```text
- Qwen 资料整理 Agent
- 自动抽取 canon facts
- entity graph
- 自动知识图谱
```

后续如果发现审计效果不够，再加入轻量模型抽取结构化 facts。

## 5. RAG Knowledge Layer 设计

### 5.1 组件选择

```text
文档解析：Docling
Chunk / ingestion：LlamaIndex
向量库：Chroma
Embedding：OpenAI text-embedding-3-small 或其他低价 embedding API
检索策略：Vector Search + BM25 + Metadata Filter
```

Docling 适合文档解析，因为官方文档说明它支持多种文档格式解析，包括高级 PDF 理解，并能与生成式 AI 生态集成。([DocLing][3])

LlamaIndex 的低层 API 支持自定义数据连接器、索引、retriever、query engine 和 reranking 模块，适合我们构建轻量但可控的 RAG 管线。([GitHub][4])

Chroma 可以用 persistent client 在本地持久化数据；官方文档说明 `PersistentClient` 会把数据存储到磁盘，适合本地开发和测试。([Chroma Docs][5])

### 5.2 RAG pipeline

```text
Upload Document
  ↓
Docling Parse
  ↓
Export Markdown / Structured JSON
  ↓
Heading-aware Chunk
  ↓
Metadata Enrichment
  ↓
Embedding
  ↓
Chroma / LanceDB Index
  ↓
Hybrid Retrieval
  ↓
Context Builder
```

### 5.3 Chunk 策略

不要简单按固定 token 硬切。DND 资料要根据内容类型切。

推荐 chunk 类型：

```text
lore_chunk
rule_chunk
spell_chunk
monster_statblock_chunk
item_chunk
npc_chunk
location_chunk
table_chunk
encounter_rule_chunk
```

每个 chunk 保存 metadata：

```json
{
  "id": "chunk_mm_00123",
  "source": "monster_manual",
  "source_title": "Monster Manual",
  "edition": "5e",
  "chunk_type": "monster_statblock",
  "title": "Young Red Dragon",
  "section_path": ["Dragons", "Red Dragon"],
  "page_start": 98,
  "page_end": 99,
  "tags": ["dragon", "fire", "cr10"],
  "text": "..."
}
```

世界观文档 chunk：

```json
{
  "id": "chunk_world_0042",
  "source": "world_bible",
  "chunk_type": "lore_chunk",
  "title": "The Moonwell and the Third Eclipse",
  "section_path": ["Cosmology", "Moonwell"],
  "canon_level": "hard",
  "tags": ["moonwell", "resurrection", "divine_magic"],
  "text": "..."
}
```

### 5.4 检索策略

不要只用向量检索。DND 资料有大量精确术语：

```text
counterspell
long rest
CR 5 undead
legendary resistance
Moonwell
third eclipse
```

推荐：

```text
Vector Search top 20
+
BM25 Search top 20
+
Metadata Filter
+
Merge & Deduplicate
+
Optional Rerank
+
Return top 6–12 chunks
```

不同 Agent 使用不同 source 权重：

```text
故事生成：
  world_bible 权重最高
  monster_manual 次高
  phb/dmg 辅助

世界观审计：
  world_bible 权重最高
  phb/dmg/mm 用于规则冲突检查

规则审计：
  phb/dmg 权重最高
  monster_manual 次高
```

## 6. LLM Agent 设计

第一版核心 LLM 节点只有两个半：

```text
1. Story Generator Agent
2. World Auditor Agent
3. Story Fixer Node
```

### 6.1 Story Generator Agent

职责：

```text
根据当前阶段、用户 brief、已确认 artifact、RAG context 生成故事草案。
```

推荐模型：

```text
默认：GPT 中高档模型
关键章节 / 最终润色：更高档 GPT
普通支线 / 小场景：更便宜 GPT mini 级别
```

输入：

```json
{
  "stage": "campaign_brief",
  "user_brief": "...",
  "committed_artifacts": [],
  "retrieved_context": [],
  "human_feedback": [],
  "constraints": {
    "party_level": 5,
    "tone": "gothic horror",
    "session_count": 3
  }
}
```

输出：

```json
{
  "title": "...",
  "pitch": "...",
  "theme": "...",
  "main_conflict": "...",
  "main_villain": {
    "name": "...",
    "motivation": "...",
    "secret": "..."
  },
  "acts": [
    {
      "title": "...",
      "summary": "...",
      "player_goal": "...",
      "dm_secret": "..."
    }
  ],
  "canon_references": ["chunk_world_0042", "chunk_dmg_0120"]
}
```

### 6.2 World Auditor Agent

职责：

```text
检查故事 artifact 是否违反世界观、规则、时间线、NPC 动机、阵营目标和语气。
```

推荐模型：

```text
DeepSeek thinking mode
temperature: 0–0.2
```

审计不要直接改故事，只输出问题。

输出：

```json
{
  "approved": false,
  "issues": [
    {
      "severity": "high",
      "category": "lore_conflict",
      "story_claim": "The Moonwell resurrects the prince after the third eclipse.",
      "conflicts_with": [
        {
          "chunk_id": "chunk_world_0042",
          "text": "The Moonwell cannot resurrect the dead after the third lunar eclipse."
        }
      ],
      "explanation": "This violates a hard canon constraint.",
      "suggested_fix": "Change the ritual from resurrection to spirit communication."
    }
  ]
}
```

审计器可拆成多个 checklist：

```text
Timeline Auditor
Lore Consistency Auditor
NPC Motivation Auditor
Faction Logic Auditor
Magic Rule Auditor
Tone Auditor
DND Rule / Balance Auditor
```

第一版可以先做一个总审计节点，后续再拆。

### 6.3 Story Fixer Node

职责：

```text
根据人类反馈或审计报告修订当前 artifact。
```

输入：

```json
{
  "previous_artifact": {},
  "human_feedback": "...",
  "audit_issues": [],
  "retrieved_context": []
}
```

输出新的 artifact 版本：

```text
new_artifact.parent_artifact_id = previous_artifact.id
new_artifact.version = previous_artifact.version + 1
```

## 7. 逐步生成流程

模组不要一次生成完整文本。采用逐层展开：

```text
Level 1: Campaign Brief
  主题、风格、核心冲突、主反派、结局方向

Level 2: Campaign Outline
  3–5 幕结构、每幕目标、关键转折

Level 3: Act Outline
  每一幕的地点、NPC、线索、遭遇

Level 4: Scene / Encounter Draft
  单个场景、战斗、社交、探索、谜题

Level 5: Final Module Text
  可交付给 DM 的正式文本
```

每一层都走同一个小循环：

```text
Generate
  ↓
Human Review
  ├── approve → Audit
  ├── request_changes → Revise → Human Review
  └── reject → Regenerate

Audit
  ↓
Human Review Audit
  ├── approve → Commit
  ├── request_changes → Revise With Audit → Human Review
  └── reject → Regenerate / Return Previous Stage

Commit
  ↓
Next Stage
```

### 8.1 高层状态

```text

GENERATING

COMMITTING
ADVANCING_STAGE

```

### 8.2 状态转移

```text
INIT
  ↓
GENERATING_CAMPAIGN_BRIEF
  ↓
WAITING_HUMAN_REVIEW_BRIEF
  ├── approve → AUDITING_BRIEF
  ├── request_changes → REVISING_BRIEF

  ↓

  ↓
...
```

### 8.4 LangGraph 节点


## 9. 回滚与版本策略

工程上不要真的“修改旧状态”。更好的做法是：

```text
从旧 artifact fork 新 artifact
```

也就是说：

```text
Artifact v1
  ↓ request_changes + feedback
Artifact v2 parent = v1
```

旧版本永远保留。

### 9.1 人类确认按钮

每个人工确认节点提供：

```text
Approve
Request Changes
Reject and Regenerate
Return to Previous Stage
```

### 9.2 行为定义

#### Approve

```text
artifact.status = human_approved
进入 audit
```

#### Request Changes

```text
创建新 artifact
parent_artifact_id = old_artifact.id
human_feedback 作为修订输入
进入 revise_artifact
```

#### Reject and Regenerate

```text
从当前 stage 重新生成
保留 rejection feedback
```

#### Return to Previous Stage

```text
回到上一个 committed artifact
从该 artifact fork 新分支
```

## 14. Provider Adapter 设计

不要在业务代码里直接散落 OpenAI / DeepSeek 调用。

定义统一接口：

```python
from pydantic import BaseModel
from typing import Any

class LLMResponse(BaseModel):
    content: Any
    input_tokens: int | None = None
    output_tokens: int | None = None
    cost_usd: float | None = None
    raw: dict | None = None

class LLMProvider:
    async def generate(
        self,
        model: str,
        messages: list[dict],
        response_schema: dict | None = None,
        temperature: float = 0.7,
        max_tokens: int | None = None,
    ) -> LLMResponse:
        raise NotImplementedError
```

实现：

```text
OpenAIProvider
DeepSeekProvider
EmbeddingProvider
```

业务代码只调用：

```python
response = await llm.generate(
    model="story-model",
    messages=messages,
    response_schema=CampaignBriefSchema.model_json_schema(),
    temperature=0.8,
)
```

## 15. Prompt 与 Schema 原则

### 15.1 所有 LLM 节点必须输出结构化 JSON

不要让下游解析自然语言。

推荐：

```text
LLM output
  ↓
JSON parser
  ↓
Pydantic validation
  ↓
失败则 retry / repair
  ↓
入库
```

### 15.2 Prompt 要包含固定 contract

例如 Story Generator prompt：

```text
你是 DND 模组故事设计助手。
你只负责生成当前 stage 的 artifact。
你必须遵守 retrieved_context 中的世界观和规则。
你不能改写已 committed 的设定。
你必须输出符合 JSON Schema 的对象。
```

### 15.3 Auditor prompt

```text
你是世界观与规则审计器。
你不负责重写故事。
你只输出 issues。
每个 issue 必须包含 severity、category、story_claim、evidence、suggested_fix。
如果没有严重问题，approved=true。
```

```text

- D&D Beyond 集成
- 完整 CR 计算器
- Agent 自主规划
- 复杂微服务
- RAGFlow / Dify 接入
```

## 18. 关键工程风险

### 18.1 RAG 检索召回不准

缓解：

```text
- chunk metadata 做好
- 使用 BM25 + vector hybrid
- 根据 stage 加 source 权重
- 检索结果显示给用户 debug
```

### 18.2 LLM 输出 JSON 不稳定

缓解：

```text
- 使用 JSON Schema / Pydantic validation
- parser 失败自动 repair
- repair 失败重试一次
- 仍失败则标记 workflow failed
```

### 18.3 人工反馈导致版本混乱

缓解：

```text
- 不修改旧 artifact
- 每次 request_changes 都 fork 新 artifact
- parent_artifact_id 串版本树
- committed artifact 单独记录
```

### 18.4 LangGraph checkpoint 与业务数据混淆

缓解：

```text
- LangGraph checkpoint 只当运行态
- artifacts / reviews / audits 必须入业务 DB
- 最终产品状态以业务 DB 为准
```

### 18.5 成本失控

缓解：

```text
- 每次 LLM 调用记录 tokens / cost
- 故事生成分层
- 审计用低价模型
- 长文档不直接塞给 GPT，必须走 RAG context
```

## 19. 最终设计结论

本项目第一版应实现为：

```text
轻量 RAG 知识层
+
LangGraph 状态机
+
GPT 故事生成
+
DeepSeek 世界观审计
+
人类确认节点
+
Artifact 版本数据库
```

核心架构不是“多 Agent 自动聊天”，而是：

```text
Human-gated generative workflow with artifact versioning
```

也就是：

> **人类把关的逐步生成工作流。**

第一版成功标准：

```text
用户上传核心资料
→ 系统完成 chunk 和检索
→ 用户输入模组需求
→ GPT 生成大草案
→ 用户确认或反馈修改
→ DeepSeek 审计
→ 用户确认审计结果
→ 草案落库
→ 系统进入下一层生成
```

这个设计工程可行性很强，复杂度主要集中在：

```text
1. Workflow 状态机
2. Artifact 版本管理
3. Human review / resume
4. RAG 检索质量
5. 审计报告结构化
```

LLM 不是系统主体，**工作流和版本化才是主体**。
